PostgreSQL · MySQL · MongoDB

Know what changes before Piper writes a byte.

Piper is a local CLI that migrates schema and data across PostgreSQL, MySQL, and MongoDB. It plans offline from a snapshot, warns on skips, widenings, and omissions its mappings know about, and touches the target only when you run execute.

How it works

Inspect. Plan. Execute. Then check the work separately.

Four commands, in that order. The plan comes from a snapshot, so reading it costs no connection to the target. The target is only for execute.

Resumable by design

Long copies get interrupted. Piper keeps progress in .piper/, so resume continues instead of starting the target over.

Validate does not trust execute

A green checklist from the tool that did the writing is a claim. Validate re-reads both databases and runs its own checks — row counts, relationship integrity, JSON values, numeric precision — instead of trusting execute's report.

During execute

Watch schema finish, then each table copy as it runs.

Follow your migration as it runs, from schema creation to data transfer, with row counts for each table and a batch progress bar for the active one. Resume clearly marks finished tables as already completed, while keeping the reminder to leave source data unchanged in view.

Source stays still

One line under the title reminds you Piper copies a static dataset — it does not sync ongoing writes.

Batch progress

Large tables show filled/empty blocks and done/total batches so a long copy is measurable, not a blank wait.

Resume is explicit

Tables finished in an earlier attempt read already completed. Partially finished ones continue from the checkpoint.

Why it exists

A migration can succeed and still be wrong.

Most tools measure whether the copy finished. Few say whether the data still means what it meant. Piper treats those as two different questions.

What the tool reported
exit code 0 14 tables copied 0 errors
Silent losses after a successful migration report
In the source What happened anyway Where Piper names it
numeric(12,2) Read back as a float. Rounding nobody planned. WARN type mapping
timestamptz Stored without its zone. The same instant reads differently. WARN type mapping
FOREIGN KEY Never recreated in the target. The log said nothing. SKIP relationship
INDEX Dropped because the target had no name for it. Queries got slower later. WARN index

So the plan says it first

For the mappings and catalog facts Piper inspects, these losses show up as plan warnings, before the first write, where you can still say no.

Plan warnings

Known skips, widenings, and omissions are named up front.

When the planner cannot preserve a fact exactly — within the type maps, index rules, and catalog objects it inspects — it records a warning before anything runs. You read those in the terminal, and they stay in the plan record. That is not a claim that every possible semantic drift is covered.

widen

The column lands in a broader type. Values survive, but the source's limit no longer applies.

omit

An index or method has no equivalent. Piper names the ones it refuses to invent a stand-in for.

skip

Piper will not migrate it. Views, triggers, routines, and relationships it cannot hold on the target are listed and left behind, not dropped quietly.

Strict mode, for when a warning should stop the line.

Use it in CI, or any time you would rather be told no than accept a skip you didn't expect.

Operator reality

A serious CLI, kept on your machine.

No account, no daemon, no telemetry. Piper is one binary, and everything it produces stays in .piper/ next to where you ran it.

Connection URLs

Come from the environment, so credentials stay out of shell history and scripts.

piper doctor

An optional preflight. Checks connectivity, direction, versions, and live-target risks before you spend time on a plan.

JSON output

Use --output json so CI can gate on the same checks and warnings you read in the terminal.

Local artifacts

Snapshots, plans, and progress live in .piper/. You can read them, commit them, or delete them.

Trust boundaries

What v1 claims, and what it refuses.

A short list of promises is easier to keep than a long one. Everything on the right is a decision, not a gap we forgot. Warnings cover mappings and catalog facts Piper inspects — not every imaginable semantic change.

Piper claims

  • Six cross-dialect directionsBetween PostgreSQL, MySQL, and MongoDB.
  • Schema and data, with a plan firstDetected plan warnings are listed before any write.
  • Resume after interruptionProgress is kept locally.
  • Independent validationValidate re-reads both sides and runs its own finite check set.
  • Local and privateSingle binary. Artifacts stay in .piper/.

Piper refuses

  • Same-dialect migrationOut of scope on purpose.
  • Full routine and trigger translationThey are named and skipped, not rewritten.
  • PostGIS as a support claimSpatial data is not a promised mapping.
  • Omniscient drift detectionUnmodeled semantic changes can still exist outside the warning and validate surfaces.
  • Live sync and CDCPiper moves a snapshot. It does not follow changes.
  • Multi-schema in one runOne schema per run.
  • Roles and grantsAccess control is not migrated.

Get started

Run doctor, then read your first plan.

Piper is one local binary per platform — macOS, Linux, and Windows, on amd64 and arm64. Download the binary alone, or a starter zip that already has it at the folder root.

No global install required. Piper runs from whatever directory you put it in — ./piper doctor (or .\piper.exe doctor on Windows) is enough. Putting it on your PATH is optional.

Checksums: downloads/SHA256SUMS. Same six targets as the GoReleaser matrix.

  1. 1

    Unzip the starter (or drop the binary in any folder) and cd into that directory.

  2. 2

    Point it at your databases with env URLs (env.example in the zip), then run the optional preflight.

    ./piper doctor
  3. 3

    Inspect, then read the plan. Nothing is written to the target yet. Pick a cross-dialect target.

    ./piper inspect && ./piper plan --target mongo
  4. 4

    Execute when the warnings are acceptable, then validate.

    ./piper execute && ./piper validate
