Your first migration

This guide walks one supported path end to end: PostgreSQL to MySQL. The goal is a first successful migration with as few decisions as possible.

Before you start

Use an empty MySQL database as the target. Keep the PostgreSQL source still while Piper runs — Piper does not take a consistent database snapshot and does not follow later writes.

What you need

  • The Piper binary (see Install)
  • PostgreSQL 14+ with a small sample schema
  • An empty MySQL 8.0+ database
  • Network access from your machine to both databases

1. Create a project folder

Piper stores artifacts in .piper/ in the current directory (unless you set --project-root).

command
mkdir my-migration && cd my-migration
# put or symlink the piper binary here

2. Prepare a small PostgreSQL source

If you already have tables, skip this and use them. Otherwise create something simple:

optional setup
psql "$PIPER_SOURCE_URL" <<'SQL'
CREATE TABLE customers (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE orders (
  id BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id),
  total_cents INTEGER NOT NULL CHECK (total_cents >= 0)
);
INSERT INTO customers (email) VALUES ('ada@example.com');
INSERT INTO orders (customer_id, total_cents) VALUES (1, 2500);
SQL

3. Point Piper at both databases

Prefer environment variables. Put passwords in PIPER_SOURCE_PASSWORD / PIPER_TARGET_PASSWORD, or let Piper prompt.

command
export PIPER_SOURCE_URL='postgres://user@127.0.0.1:5432/appdb?sslmode=disable'
export PIPER_TARGET_URL='mysql://user@127.0.0.1:3306/appdb'
# export PIPER_SOURCE_PASSWORD='…'
# export PIPER_TARGET_PASSWORD='…'

More options: Connecting databases.

4. Optional preflight

command
./piper doctor

doctor checks connectivity, versions, and safety notes. Warnings here do not block you — they tell you what to read next.

5. Inspect the source

command
./piper inspect
Illustrative output
$ piper inspect
Inspected PostgreSQL · 2 entities
Run  run_01J…
Next  piper plan --target <dialect>

Piper connects to the source, reads tables and relationships, and writes a schema snapshot to .piper/runs/<run-id>/ir.json. Nothing is written to MySQL yet.

6. Plan for MySQL

command
./piper plan --target mysql

Important

--target defaults to postgres. For a PostgreSQL source you must pass --target mysql (or mongo). Same-dialect plans are rejected.

Read the warnings. Piper lists skips, type changes, and anything it will not recreate. The same findings are in the plan JSON if you want to gate on them later with --output json.

Plan does not need a live target connection. It works from the saved inspect snapshot.

7. Execute

command
./piper execute

Piper creates schema on the target, copies rows in batches, then applies relationships. Progress shows tables and row counts. On a lossy plan, Piper may ask you to confirm; pass --yes to skip prompts.

Illustrative output — real completion copy
$ piper execute
Migration completed.
Next  piper validate

If the target already has data

A new run expects the planned tables to be empty. Existing rows stop execute until you pass --recovery continue or --allow-existing-target. Those start over with no inherited checkpoints. Prefer an empty database for a first run.

8. Validate

command
./piper validate

Validate re-checks row counts, planned foreign keys, and a few fallback cases. It does not trust the green execute checklist alone. Exit code 5 means a check failed.

If something stops halfway

  1. ./piper explain — latest failure and a suggested next step
  2. ./piper resume — continue from the last completed batch (finished tables stay; they are not undone)
  3. ./piper status — current run state

There is no piper pause command. If the process stops, resume continues from the last completed batch under the project lock.

What you should have now

  • Tables and rows on MySQL
  • Artifacts under .piper/runs/<run-id>/
  • A validation report you can re-run any time
